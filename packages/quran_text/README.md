# quran_text

Канонический текст, технические ключи, сходство слов, поиск последовательностей.

- **Владелец:** Opus
- **Задача:** [P02](../../docs/tasks/P02-quran-text.md)
- **ТЗ:** 10.1, 12.2, 12.3 (`normalizer.json`), 17.2

Правила: [`AGENTS.md`](../../AGENTS.md). Публичный интерфейс — только `lib/quran_text.dart`; внутренности — в `lib/src/`. Чистый Dart, без Flutter.

## Что внутри

| Часть | Что делает |
|---|---|

| `InMemoryQuranText` | Реализация: слова в памяти, ключи, индекс троек и словарь ключей строятся один раз на каждый нормализатор (или ключи берутся из кэша). Канон не копируется и не меняется |
| `QuranTextSource`, `QuranTextJsonSource`, `ContentJsonSource` | Источник слов. `QuranTextJsonSource` — **текст всего Корана** (формат 2, ADR 0004; `packages/testing/fixtures/quran_text.json`); `ContentJsonSource` — страницы прототипа (формат 1, `content_p582_583.json`) |
| `SearchKeyCache` | Интерфейс кэша ключей в базе пользователя (`search_key_cache`, ТЗ 12.1; таблицу делает `storage`, O04) |
| `Normalizer` | Нормализатор по `normalizer.json` (ТЗ 12.3) и встроенный по шагам ТЗ 10.1 |
| `similarity`, `levenshtein`, `boundedLevenshtein`, `maxEditsFor` | `1 − Левенштейн / длина большего`, по кодовым точкам; ограниченный вариант бросает сравнение, как только расстояние превысило предел |
| `findSimilarPlaces` | Пары похожих мест текста по ключам: повторяющиеся аяты и общие обороты (D01, `similar_pair`); параметры — `SimilarPlaceParams` |

## Ключи — не текст

`SearchKey` и `NormalizerId` — отдельные типы (extension type), а не `String`: ключ нельзя случайно передать туда, где ждут текст для показа. `Word.text` — только канон. Страницы и строки у `Word` нет: разметка — отдельный пакет и только для страниц с правами (ADR 0004). `SearchKey` объявлен в `contracts` (его несёт путь выравнивания, ADR 0003) и переэкспортируется отсюда.

## Нормализатор

Шаги по порядку: Unicode NFC (если `nfc`), удаление кодовых точек из `removeRanges`, замены из таблицы `replace` по порядку строк, удаление разделителя и пробелов внутри слова. Скрытых правил нет: всё — из таблицы.

Формат `normalizer.json` (в ТЗ 12.3 перечислены только поля, точный вид — здесь):

```json
{
  "id": "quran-asr-small-1",
  "nfc": true,
  "removeRanges": [{"from": "0640", "to": "0640"}, {"from": "064B", "to": "0652"}],
  "replace": [{"from": "…", "to": "…"}],
  "wordSeparator": " "
}
```

Кодовые точки — шестнадцатеричные, диапазон включает оба конца, `nfc` по умолчанию `true`.

**Встроенный нормализатор** (`builtin-10.1`) — шаги 1, 2, 3 и 5 ТЗ 10.1: NFC, удаление татвиля U+0640, огласовок U+064B–U+0652 и знаков U+06D6–U+06ED, пробелов внутри слова. Шаг 4 (надстрочный алиф, варианты алифа, хамза, ى/ي, ة/ه) в нём **не делается**: ТЗ требует делать его строго по таблице модели, а таблицы ещё нет. Её даст пакет модели (P04 и испытание моделей).

## Поиск

Распознанные слова режутся на тройки (`ngramSize`); каждая тройка голосует за место, где стояло бы первое искомое слово; места с наибольшим числом голосов — первые, при равенстве — раньше по тексту. Меньше трёх слов — ничего не найдено.

`findSequence` возвращает `SequenceMatch` (место + число совпавших троек), а не голый `WordKey`, как в наброске ТЗ: число совпадений нужно `follow` для выбора кандидата. Параметр `normalizer` добавлен, потому что индекс свой у каждого нормализатора.

## Нечёткий поиск по всему Корану

`findSimilar(keys, minSimilarity, maxMeanCost)` ищет места, где искомые слова стоят подряд и каждое похоже на слово текста не меньше чем на `minSimilarity`, а среднее `1 − сходство` не больше `maxMeanCost`. Оба предела — параметры (`follow` передаёт `simFloor` и `lostCostThreshold`, ТЗ 12.4).

Как устроен:

1. Словарь различных ключей с их местами, разложенный по длине ключа.
2. Для каждого искомого слова — похожие ключи словаря. Ключи, у которых длина слишком отличается, пропускаются сразу; остальные сравниваются с пределом числа правок, и сравнение бросается, как только предел превышен. Предел (`maxEditsFor`) — наибольшее `d`, при котором `1 − d / длина большего ≥ minSimilarity`, проверенное тем же выражением, что и сходство: граница включается точно. Просто `⌊(1 − minSimilarity) × длина⌋` ошибается из-за округления: `(1 − 0,8) × 5 = 0,9999999999999998`, и слово из 5 букв с одной ошибкой при пороге 0,8 не находилось (нашла Астра, №21).
3. Места перебираются от слова с наименьшим числом мест; каждое место проверяется целиком.

## Замеры (весь Коран)

`tool/benchmark.dart`, скомпилированный Dart, компьютер (Intel Xeon 2,1 ГГц, 4 ядра), встроенный нормализатор:

| Что | Время |
|---|---|
| Чтение текста (77 433 слова) | ≈ 40 мс |
| Ключи всех слов | ≈ 220 мс |
| Индекс троек и словарь из готовых ключей | ≈ 80 мс |
| Точный поиск 3 слов (`findSequence`) | < 0,01 мс |
| Нечёткий поиск 3 слов (`findSimilar`) | ≈ 20 мс |
| Память процесса с текстом и индексами | ≈ 83 МБ (из них ≈ 6 МБ — сама среда Dart) |

**Оценка для бюджетного Android** (в 3–5 раз медленнее, замер на телефоне — владелец, П-09): ключи ≈ 0,7–1,1 с, индекс из кэша ≈ 0,25–0,4 с, нечёткий поиск ≈ 60–100 мс.

**Что кэшировать.** Дорогая часть — ключи, поэтому их строим один раз при установке модели в отдельном изоляте и храним в `search_key_cache` (`normalizer_id`, `word_index`, `key`) через `SearchKeyCache`; запись действительна для того же нормализатора и той же версии текста. Индекс троек и словарь перестраиваются из ключей в памяти (≈ 0,1 с на компьютере), поэтому `ngram_cache` необязателен; если замер на телефоне покажет больше 0,5 с — хранить и его.

## Не сделано в v0

- `similarPairs` из ТЗ 10.1 в интерфейсе `QuranText` пока нет: пары считает `findSimilarPlaces` при сборке содержания (D01), а читать их из базы содержания будет приложение.
- Ключи и индекс строятся в памяти; хранение в базе пользователя (`search_key_cache`, `ngram_cache`) — задача `storage`.
- Нечёткий поиск требует, чтобы искомые слова стояли подряд: пропущенное или лишнее слово внутри окна он не прощает (это делает выравнивание в `follow`).
