# session

Сессия чтения: звук → распознавание → следование → проверка.

- **Владелец:** GPT-B
- **Задача:** S05
- **ТЗ:** 4.3, 4.5, 4.6, 10.6

Правила: [`AGENTS.md`](../../AGENTS.md). Публичный интерфейс — только `lib/session.dart`; внутренности — в `lib/src/`.

## Публичный API

`ReadingSession` получает через конструктор только договоры и доменные
зависимости: `SessionAudioSource`, `SpeechRecognizer`, `QuranText`,
нормализатор, версии и параметры `follow`/`check`. Команды экрана передаются в
`execute(SessionCommand)`, события читаются из `events`, состояния — из
`states` и синхронного `state`.

Состояния идут по ТЗ 10.6:

```text
idle → preparing → ready → listening ⇄ paused → finishing → finished
                     ↘ error(modelMissing | micDenied | deviceTooSlow)
```

При `Stop` источник сначала отдаёт хвостовые кадры и закрытия. Затем сессия
ждёт окончательные `RecognitionResult` всех закрытых отрезков, завершает
`follow` и переводит оставшиеся предварительные ошибки в `unverified`.
`SessionFinished` содержит ровно один итог каждого слова диапазона. Слова после
места остановки получают `notRead`, а не `error`.

В строгом режиме `strictSignals` передаёт экрану `WaitForWord`, `OfferHint` и
`StopWaiting`. После `WaitForWord` сессия удерживает новые открытия слов до
прочтения ожидаемого слова или подсказки. Периодический `tick` продолжает
проверять предел ожидания даже при отсутствии новых результатов распознавания.

`SessionCheckpointStore`, если передан, получает состояние каждые 30 секунд,
при паузе и завершении. В checkpoint нет звука и распознанного текста.

## Потоки выполнения

Для приложения публичной точкой входа служит `ReadingSessionIsolate.spawn`.
Платформенный `SessionAudioSource` передаётся отдельно и остаётся в корневом
Flutter-изоляте: `record.startStream()` и `onStateChanged()` используют
`EventChannel`, обработчики которого нельзя регистрировать в background
isolate. Factory получает не платформенный объект, а портовый proxy и создаёт с
ним `ReadingSession` в долгоживущем worker.

Команды сессии имеют request id и явный `Result`. Команды источника
`start/pause/resume/stop/dispose` идут обратно в корневой изолят через отдельный
порт. Открытия и закрытия отрезков и качество идут в worker сообщениями, а PCM
каждого кадра переносится без обычного копирования через
`TransferableTypedData`. События сессии, состояния, строгие сигналы и безопасные
ошибки возвращаются отдельными потоками. После отказа worker новые команды
сразу получают `Result.error`; при `dispose` завершаются все ожидающие запросы,
освобождается корневой источник и закрываются все порты.

Итоговая схема выполнения:

- корневой Flutter-изолят держит только платформенную часть `audio_capture` и
  пересылает её события;
- worker `audio_capture` по-прежнему держит VAD, кольцевой буфер и оценку
  качества, получая PCM от корневой платформенной части;
- session worker держит `ReadingSession`, `follow` и `check`;
- worker `asr_sherpa` держит sherpa-onnx и декодирование.

Таким образом, Flutter `EventChannel` работает в поддерживаемом изоляте, а VAD,
ASR, оркестрация, следование и проверка не выполняются в UI-цикле. Звук не
копится в `session` и не пишется на диск. На телефоне всё равно нужна проверка
НФ-10 и плавности интерфейса.

## Конфиденциальность

Аудиокадр сразу передаётся `SpeechRecognizer.acceptAudio`; пакет его не пишет
на диск и не журналирует. Распознанный текст остаётся тем, что вернула модель,
и никогда не заменяется ожидаемым каноническим текстом.
