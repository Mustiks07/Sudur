# 17. Инженерные правила

Как писать код Sudur: архитектура, надёжность, безопасность, скорость, тесты. Правила собраны из официальных источников (список в конце) и привязаны к нашим модулям. Для агентов краткая выжимка лежит в `AGENTS.md`.

## 17.1 Архитектура по официальному руководству Flutter

У Flutter есть официальное руководство по архитектуре и пример приложения Compass на GitHub. **Решение [Р]:** строим по нему. У агентов будет эталон, а у владельца — понятная схема, по которой проверять их работу.

### Слои

| Слой | Части | Что делает | От чего может зависеть |
|---|---|---|---|
| **Интерфейс** | **Экран (View)** | Показывает данные, принимает нажатия. Логики почти нет: показать или скрыть элемент, анимация, раскладка под размер экрана, переход между экранами | Только от своей модели экрана |
| | **Модель экрана (ViewModel)** | Превращает данные в состояние экрана, хранит его, даёт экрану команды | От хранилищ и сценариев, через конструктор |
| **Логика** | **Сценарии и правила** | Сложная логика, общая для нескольких экранов: следование, проверка, план, уроки | От хранилищ и договоров; на чистом Dart |
| **Данные** | **Хранилище (Repository)** | Единственный источник правды для своих данных: кэш, ошибки, повторы, синхронизация | Только от сервисов. Хранилища друг от друга не зависят |
| | **Сервис (Service)** | Обёртка над одним внешним источником: микрофон, модель, база, сеть, магазин. Состояния не хранит | Ни от чего в приложении |

**Поток данных — в одну сторону** [Ф]:

1. Нажатие на экране вызывает команду модели экрана.
2. Модель экрана вызывает хранилище или сценарий.
3. Хранилище меняет данные и возвращает новые.
4. Модель экрана сохраняет новое состояние.
5. Экран перерисовывается.

Данные меняются только в слое данных.

### Как это ложится на наши пакеты (раздел 4.1)

| Слой | Где у нас |
|---|---|
| Экраны и модели экранов | `app/lib/ui/<функция>/views/`, `app/lib/ui/<функция>/view_models/`; общие элементы — `app/lib/ui/core/` |
| Сценарии и правила | `follow`, `check`, `session`, `planner`, `lessons`, `quran_text` — чистый Dart |
| Договоры и модели предметной области | `contracts` — неизменяемые модели, интерфейсы хранилищ и сервисов |
| Хранилища | `app/lib/data/repositories/` — абстрактный класс плюс реализации |
| Сервисы | `audio_capture`, `asr_sherpa`, `storage` (drift), `content`, `entitlements` (RevenueCat), `sync` (Supabase) |

### Рекомендации руководства и наше решение

| Рекомендация Flutter | Уровень [Ф] | У нас |
|---|---|---|
| Чёткие слои интерфейса и данных | Настоятельно | Да |
| Хранилища в слое данных | Настоятельно | Да |
| Экран + модель экрана (MVVM) | Настоятельно | Да |
| Никакой логики в виджетах | Настоятельно | Да |
| Данные в одну сторону | Настоятельно | Да |
| Неизменяемые модели данных | Настоятельно | Да; генерация через `freezed` — для моделей в `contracts` |
| Внедрение зависимостей | Настоятельно | Да, пакет `provider`, как в примере Compass |
| Абстрактные классы хранилищ | Настоятельно | Да |
| Тестировать части по отдельности и вместе | Настоятельно | Да |
| Подделки (fakes) для тестов | Настоятельно | Да; моки — только для внешних библиотек |
| Команды для действий пользователя | Рекомендуется | Да |
| go_router | Рекомендуется | Да |
| Единые имена: `HomeScreen`, `HomeViewModel`, `UserRepository`, `AudioService` | Рекомендуется | Да |
| Отдельный слой логики | По ситуации | Да — проверка и план слишком сложны для моделей экранов |
| Отдельные модели для сети и для приложения | По ситуации | Да, для синхронизации |

### Изменение решения из раздела 4.7 [Р]

Было: состояние экранов — Riverpod. Стало: **модель экрана на `ChangeNotifier`, экран слушает её через `ListenableBuilder`, зависимости — через `provider`, ошибки — тип `Result`, действия — команды**. Так устроен официальный пример. Riverpod руководство называет как допустимую альтернативу; мы выбираем вариант, у которого есть официальный эталон. Пересмотреть, если модели экранов станут неудобны.

## 17.2 Правила кода

### Обработка ошибок

- Между слоями ошибки передаются **типом `Result`** (`Ok` / `Error`), а не исключениями: исключения в Dart не проверяются компилятором и приводят к падениям [Ф: руководство Flutter].
- Сервис ловит исключения библиотеки и превращает их в `Result.error` с понятным типом ошибки.
- Пустых `catch` нет. Ошибка либо обрабатывается, либо передаётся дальше, либо записывается в журнал.
- Каждая модель экрана показывает состояния: загрузка, данные, ошибка — человеку понятным текстом.

### Строгость языка

- `analysis_options.yaml`: набор `very_good_analysis` плюс строгие режимы `strict-casts`, `strict-inference`, `strict-raw-types`.
- Без `dynamic` и без `!` на nullable без комментария, почему значение точно есть.
- Без `print` — только журнал.
- Без глобального изменяемого состояния и самодельных синглтонов: всё — через внедрение зависимостей.
- **Время и случайность внедряются** (`Clock`, `Random`): иначе планировщик не протестировать.

### Неизменяемость и модели

- Модели предметной области — неизменяемые, с `copyWith` и сравнением по значению (`freezed`).
- Канонический текст Корана — только чтение. Ни одна функция не возвращает изменённый канон (раздел 4.8).

### Порядок в коде

- Файл — одна главная сущность. Имена — по роли: `ReadingScreen`, `ReadingViewModel`, `SessionRepository`, `AsrService`.
- Публичный интерфейс пакета — только через `lib/<пакет>.dart`; внутренности — в `lib/src/`.
- Пороги и параметры — только из конфигурации (раздел 12.4).
- Строки интерфейса — только из ARB-файлов локализации.

## 17.3 Безопасность

Опора — стандарт OWASP MASVS v2: 24 требования в 8 группах. Ниже — что это значит для Sudur. Формулировки групп даны по моему знанию стандарта; полный текст требований сверять на mas.owasp.org.

| Группа MASVS | Что делаем |
|---|---|
| **STORAGE** — хранение | Токены входа — только в `flutter_secure_storage` (Keychain на iOS, Keystore на Android). Звук на диск не пишется (ЗВ-02). Сохранённые записи — в личной папке приложения, вне резервных копий. В журналах нет звука, распознанного текста, токенов и личных данных |
| **CRYPTO** — криптография | Свою криптографию не пишем. Проверка подписи манифеста — проверенной библиотекой Ed25519; контрольные суммы — SHA-256; случайные числа — `Random.secure()` |
| **AUTH** — вход и права | Вход Google и Apple через Supabase Auth, короткоживущие токены с обновлением. На сервере права проверяет RLS (17.4), а не приложение |
| **NETWORK** — сеть | Только HTTPS: на Android открытый HTTP запрещён настройкой сети, на iOS — App Transport Security по умолчанию. Целостность пакетов содержания обеспечивает подпись манифеста (11.4). Привязка сертификатов (pinning) в V1 не делается: она усложняет работу, а пакеты и так защищены подписью |
| **PLATFORM** — платформа | Наружу открыт только главный экран (`exported`); глубокие ссылки проверяются; встроенного браузера нет — политика конфиденциальности открывается во внешнем браузере |
| **CODE** — качество | Flutter и зависимости обновляются раз в месяц; проверка известных уязвимостей зависимостей (OSV-Scanner понимает pub). **Всё, что пришло извне, проверяется:** пакеты (подпись, схема, размер), ответы сервера, ссылки, файлы |
| **RESILIENCE** — защита от взлома | Выпускные сборки с `--obfuscate --split-debug-info`. Проверка подписки — на стороне RevenueCat, не в приложении. Защита сервера записей от злоупотреблений (Play Integrity, App Attest) — V2 |
| **PRIVACY** — приватность | Минимум данных, согласия, удаление, честные сведения в магазинах (раздел 6.2) |

### Опасные места именно у нас

| Где | Риск | Правило |
|---|---|---|
| Распаковка пакетов содержания | Архив с путями вида `../../` перезапишет файлы приложения (zip-slip) | Каждый путь из архива проверяется: после нормализации он внутри целевой папки; иначе пакет отвергается |
| Резервная копия Android | Восстановленные из копии данные `flutter_secure_storage` не расшифруются [Ф: страница пакета] | В правилах резервного копирования исключить файл `flutter_secure_storage`, оставить базу пользователя (ДН-03) |
| Ключи | Секретный ключ Supabase в приложении даёт полный доступ к базе в обход RLS [Ф] | В приложении — только публикуемый ключ; секретный — только на сервере, по отдельному ключу на каждый серверный компонент |
| Журналы | Утечка личных данных | Ключи и токены в журнал не пишутся; при необходимости — первые 6 символов или хэш [Ф: Supabase] |
| Загрузка записей | Чужие загрузки, переполнение хранилища | Одноразовые ссылки, подпись запросов ключом установки, лимит на установку (11.7) |

## 17.4 Сервер: Supabase

Правила со страниц Supabase о RLS и ключах [Ф].

- **RLS включён на каждой таблице**, доступной через API. Без RLS таблицу может читать и менять любой, у кого есть права.
- Права (grants) и политики — разные проверки: отозвать лишние права у `anon` и `authenticated`, выдать только нужные.
- **Одна политика на действие** (чтение, вставка, изменение, удаление), каждая `to authenticated`; не использовать `for all`.
- В политиках — `(select auth.uid()) = user_id` и проверка `auth.uid() IS NOT NULL`.
- **Индекс на каждом столбце из политик** (`user_id`).
- Права пользователя не хранить в `raw_user_meta_data`: человек может их изменить.
- Представления (views) — с `security_invoker = true`, иначе они обходят RLS.
- Функции `security definer` — с `set search_path = ''` и не в открытой схеме.
- Для изменения строки нужна и политика на чтение.
- **Тесты политик** — pgTAP (`supabase test db`): разрешённая запись проверяется по числу изменённых строк, а не по отсутствию ошибки.
- Старые ключи `anon` и `service_role` Supabase выводит из оборота к концу 2026 года — сразу использовать новые публикуемые и секретные ключи.

## 17.5 Скорость

### Бюджет кадра [Ф]

- 60 Гц — около 16 мс на кадр; 120 Гц — меньше 8 мс.
- Мерить только в режиме `--profile` на настоящем телефоне, самом слабом из эталонных (раздел 5.1). Режим отладки скорость искажает.
- Инструменты: DevTools — шкала кадров, наложение производительности, «Track layouts».

### Правила отрисовки [Ф]

- `build()` — лёгкий; большие методы делятся на виджеты; `setState` и уведомления — на минимальное поддерево.
- Списки — только ленивые (`ListView.builder`).
- Не использовать `Opacity` для текста и простых фигур — рисовать полупрозрачным цветом. **У нас это прямо касается скрытых слов мусхафа (11.3).**
- Не использовать обрезку и `saveLayer` без нужды; скругления — через `borderRadius`.
- Каждая страница мусхафа — в своей `RepaintBoundary`; текущее слово перерисовывается без перерисовки всей страницы.

### Фоновые изоляты [Ф]

- Тяжёлая работа длиннее кадра — не в основном изоляте.
- **Сессия чтения — долгоживущий изолят** (раздел 4.3): у каждого запроса номер, ошибки возвращаются явно, порты закрываются при выходе.
- Короткая разовая работа (например, разбор большого JSON пакета) — `Isolate.run`.
- В фоновом изоляте нельзя трогать интерфейс и `rootBundle`. Если изоляту нужны плагины — передать `RootIsolateToken` и вызвать `BackgroundIsolateBinaryMessenger.ensureInitialized`. sherpa-onnx работает через FFI, ему это не нужно.
- База — drift в своём фоновом изоляте.

### Размер и запуск

- Мерить размер по App Bundle в Play Console и отчёту App Store Connect, а не по отладочной сборке; `--analyze-size` для сравнения.
- Выпуск — с `--split-debug-info`; картинки сжаты; неиспользуемые ресурсы удалены.
- Тяжёлое (модель, шрифты всех страниц) не загружается при запуске — только когда нужно.

## 17.6 Тесты

- `test/` повторяет структуру `lib/`.
- **Модели экранов** тестируются без Flutter, с подделками хранилищ.
- **Хранилища** — с подделками сервисов.
- **Экраны** — виджет-тесты с настоящей моделью экрана и поддельными хранилищами.
- **Подделки** лежат в общем пакете `testing/` и переиспользуются.
- Плюс снимки экранов мусхафа, прогон набора записей, тесты миграций, pgTAP для сервера (разделы 5.6, 14).
