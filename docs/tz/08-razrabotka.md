# 8. Как ведётся разработка

Как работаем с кодом каждый день: репозиторий, ветки, проверки, сборки, выпуски, ключи и работа ИИ-агентов. Архитектура кода — в разделе 4, общие правила для агентов — в разделе 7.4.

## 8.1 Рабочее место [Р]

| Что | Решение |
|---|---|
| Код | Закрытый репозиторий на GitHub |
| Версия Flutter | Закреплена для всего проекта через FVM (файл `.fvmrc`); обновление — отдельной задачей |
| Android | Разработка и проверка на Windows: Android Studio, телефоны Samsung владельца, 1–2 дешёвых Android |
| iOS | Мак друга — запуск на iPhone и замеры скорости; облачная сборка — выпуски |
| Сервер записей (раздел 4.12) | Хранилище с S3-совместимым доступом в Казахстане и маленькая функция, выдающая одноразовые ссылки на загрузку; поставщик — после ЮР-01 |
| Сайт | Простая страница (например, GitHub Pages): политика конфиденциальности на трёх языках, контакты — её требуют магазины |

## 8.2 Язык и стиль кода [Р]

| Правило | Решение |
|---|---|
| Имена в коде и комментарии | Английский: так лучше работают инструменты и ИИ-агенты |
| Документы, записи решений, описания задач | Русский |
| Строки интерфейса | Только в файлах локализации (ARB): русский, казахский, узбекский |
| Строгость анализатора | Набор правил `very_good_analysis` плюс строгие режимы `strict-casts`, `strict-inference`, `strict-raw-types`; ноль предупреждений. Подробные правила кода — раздел 17 |
| Форматирование | `dart format`, проверяется автоматически |
| Ошибки | Без «тихого» перехвата исключений; человеку — понятное сообщение на его языке |
| Журналы | Пакет `logging`; в выпускной сборке — только предупреждения и ошибки, без звука, распознанного текста и личных данных |

## 8.3 Ветки и изменения [Р]

1. Ветка `main` защищена: изменения попадают только через запрос на слияние (pull request) с зелёными проверками.
2. Одна задача — одна ветка: `feature/<пакет>-<коротко>`, `fix/<пакет>-<коротко>`.
3. Сообщения изменений — по правилу Conventional Commits: `feat(check): подтверждение пропуска по двум словам`.
4. В описании запроса на слияние: номера требований (например, `ПО-03`), как проверено, снимки экрана для изменений интерфейса.
5. Каждый запрос на слияние проходит автоматическую ИИ-проверку кода (например, `/code-review`) и смотрится владельцем.
6. Сливает владелец. Без его явного одобрения не сливаются изменения в `contracts`, тексте Корана и содержании, разрешениях и приватности, покупках, настройках выпуска (раздел 7.4).

## 8.4 Задачи [Р]

- Каждое требование ТЗ становится задачей (issue) на GitHub с меткой его номера и модуля.
- Этапы раздела 7.1 — вехи (milestones).
- Порядок задач внутри этапа выбирает владелец.

**Задача готова, когда:**

- требования из задачи выполнены, их критерии приёмки проверены;
- есть тесты; все автоматические проверки зелёные;
- обновлены README пакета и, если было решение, запись в `docs/adr/`;
- новые строки интерфейса есть на трёх языках или отмечены для перевода;
- изменения звука, распознавания и интерфейса проверены хотя бы на одном настоящем Android;
- владелец одобрил.

## 8.5 Работа с ИИ-агентами [Р]

| Правило | Как |
|---|---|
| Правила лежат в репозитории | Файл `AGENTS.md` в корне (и `CLAUDE.md`, ссылающийся на него): правила разделов 7.4 и 17, команды сборки и проверок, структура пакетов. Агент читает его автоматически. Оба файла лежат в корне репозитория |
| У каждого пакета — README | Назначение, публичный интерфейс, запреты, как тестировать |
| Задание агенту | Номера требований, пакет, критерии приёмки, ссылки на разделы ТЗ |
| Один пакет — один агент одновременно | Два агента не правят один пакет параллельно; разные пакеты — можно |
| Договоры заморожены | После этапа 3 `contracts` меняются только через запись решения и одобрение владельца |
| ТЗ — в репозитории | Папка `docs/tz/`; изменения ТЗ — тоже через запрос на слияние |

## 8.6 Автоматические проверки (CI) [Р]

Сервис — GitHub Actions; сборки iOS — Codemagic или GitHub Actions с macOS, только для выпусков.

| Когда | Что проверяется |
|---|---|
| Каждый запрос на слияние | Форматирование, анализатор, автотесты, правила зависимостей (раздел 4.2), сборка Android |
| Изменён `mushaf_view`, шрифты или разметка | Снимки экранов 30 страниц (раздел 5.6) |
| Изменены `follow`, `check`, `quran_text` | Прогон набора записей, сравнение с прошлым результатом (раздел 5.5) |
| Изменён `storage` | Тесты миграций |
| Изменены `content`, `content_build` | Проверка схемы манифеста, лицензий, канона (ПР-02, ПР-04) |
| Ветка выпуска | Сборки Android и iOS, отправка во внутреннее тестирование |

## 8.8 Параметры без выпуска новой версии [Р]

Пороги проверки, лимит бесплатной проверки (10 минут), доли плана, длина пауз — в подписанном файле конфигурации, который приходит через манифест (раздел 4.9). Приложение хранит последнюю проверенную копию и встроенные значения по умолчанию. Так можно поправить параметр за день, не дожидаясь проверки магазинами.

Пороги, привязанные к модели, приходят в пакете модели (РС-02).

## 8.9 Версии и выпуски [Р]

- **Версия приложения** — `основная.дополнительная.исправление+сборка` (например, `1.2.0+45`). Пакеты содержания и модели имеют свои версии (раздел 4.9).
- **Путь выпуска:** внутреннее тестирование → закрытый тест (Google Play, TestFlight) → постепенный выпуск: в Google Play 10% → 50% → 100%, в App Store поэтапный выпуск.
- **Отката в магазинах нет**: при серьёзной ошибке выпускается исправление; поэтому постепенный выпуск обязателен.
- **Перед выпуском** — чек-лист: проверки раздела 5.6, тексты для магазинов и «что нового» на трёх языках, сведения о приватности, проверка покупок в тестовом режиме.
- **Страница в магазинах:** название, описания и снимки экранов на трёх языках, категория «Образование», возрастной рейтинг.

## 8.10 Ключи и секреты [Р]

| Ключ | Где хранится | Если потерять |
|---|---|---|
| Ключ загрузки Android | Секреты CI + две резервные копии у владельца | С подписью приложений Google Play восстанавливается через поддержку Google |
| Сертификаты Apple | Секреты облачной сборки, аккаунт Apple | Перевыпускаются в аккаунте |
| Закрытый ключ подписи манифеста (Ed25519) | Только у владельца: менеджер паролей + резервная копия вне компьютера. Не в репозитории и не в CI | Приложения не примут новые пакеты, пока не выйдет версия с новым открытым ключом. Поэтому в приложение встроены два открытых ключа: основной и запасной |
| Ключ API RevenueCat | Публичный ключ — в сборке (так задумано RevenueCat); секретные — только в CI | Перевыпускается |
| Доступ к хранилищу записей | Только у функции, выдающей ссылки | Перевыпускается |

В репозитории секретов нет; это проверяется автоматически.

## 8.11 Зависимости [Р]

- Версии закреплены в `pubspec.lock`.
- Раз в месяц — проверка обновлений отдельной задачей.
- Новая зависимость — с коротким обоснованием и проверкой лицензии; отчёт о лицензиях собирается автоматически и сверяется с реестром (раздел 6.1).

## 8.12 После запуска

| Что | Кто и как |
|---|---|
| Сообщения в Telegram | Владелец; ответ в течение 2 дней [Г] |
| Отчёты о сбоях (по согласию) | Просмотр раз в неделю; падения выше порога НФ-20 — исправление вне очереди |
| Сервер записей | Проверка заполненности и резервных копий раз в неделю |
| Обновление содержания | Через пакеты, без выпуска приложения |
