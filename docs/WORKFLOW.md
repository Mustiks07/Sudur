# Как работает команда

## Кто есть кто

| Агент | Модель | Роль | Чем владеет |
|---|---|---|---|
| **Opus** | Claude Opus 5.5 | Логика и данные: всё, где важна точность | `tools/content_build`, `packages/quran_text`, `packages/follow`, `packages/check`, `tools/eval` |
| **GPT-A** | GPT 5.6 | Приложение и интерфейс | `app/`, `packages/mushaf_view`, позже экраны |
| **GPT-B** | GPT 5.6 | Звук и распознавание | `packages/audio_capture`, `packages/asr_sherpa`, позже `packages/session`, `packages/storage` |
| **Астра** | GPT-6 | Интегратор: проверяет и сливает работу, держит `main` зелёным, собирает прототип | Корневые файлы, `packages/contracts`, `AGENTS.md`, `docs/`, `.github/` |
| **Владелец** | — | Решения, проверка на телефонах, записи чтения | Всё |

## Ветки

- `main` — всегда рабочая. Напрямую в неё не пишет никто: изменения попадают только через запрос на слияние.
- Одна задача — одна ветка: `<агент>/<номер>-<коротко>`, например `opus/p06-follow`.
- Ветки первой волны уже созданы (список в [`tasks/README.md`](tasks/README.md)). Следующие ветки агент создаёт сам от свежего `main`.

## Порядок работы над задачей

1. Взять задачу из [`tasks/`](tasks/README.md), прочитать её, `AGENTS.md` и указанные разделы ТЗ.
2. Перейти на свою ветку и подтянуть свежий `main`: `git fetch origin && git rebase origin/main`.
3. Работать **только в путях из задачи**.
4. Перед запросом на слияние: снова `git rebase origin/main`; формат, анализатор, тесты — зелёные.
5. Открыть запрос на слияние в `main`. Заголовок: `[P06] follow v0`. В описании: номера требований, как проверено, что не сделано.
6. Астра проверяет по ТЗ и `AGENTS.md` и пишет вердикт: «можно сливать» или список правок. Сливает владелец кнопкой «Create a merge commit» (не squash).

## Если нет доступа к GitHub на запись

В облачной среде GPT-агентов (GPT-A, GPT-B, Астра) отправка в GitHub не работает: `could not read Username`, API отвечает `401`. Не тратить время на повторные попытки.

- **Агент с готовой работой** упаковывает ветки в файл и отдаёт его владельцу:
  `git bundle create /tmp/sudur-<агент>.bundle <ветка> [<ветка>…] ^origin/main`, затем `git bundle verify`. В отчёте — хэши последних коммитов, SHA-256 и размер файла. Владелец передаёт файл помощнику, тот проверяет и отправляет ветки.
- **Астра** проверяет запросы на слияние, читая репозиторий, и пишет решение в отчёте владельцу: «можно сливать» или список правок для автора. Владелец пересылает правки автору.
- **Слияние** делает владелец кнопкой на GitHub (или просит помощника). Для цепочки №1 → №2 → №3 — «Create a merge commit», а не squash: тогда следующие запросы цепочки не нужно перебазировать.

## Если нужно поменять чужое

- **Договоры** (`packages/contracts`): не менять самим. Описать нужное изменение в запросе на слияние или черновиком в `docs/adr/`; решает Астра вместе с владельцем.
- **Корневые файлы** (`pubspec.yaml`, `analysis_options.yaml`, `.github/`, `AGENTS.md`): только Астра. Исключение — задача P01, которой это прямо разрешено.
- **Чужой пакет**: не трогать; написать владельцу пакета через описание запроса на слияние.

## Порядок слияния первой волны

CI в `main` уже зелёный, поэтому готовые запросы не ждут P01: сливаются, как только Астра сказала «можно».

1. **P03 → P02 → P06** (Opus) — данные суры, текст и ключи, следование. Затем **M01** и **S04**.
2. **P04, P05** (GPT-B) — распознаватель и микрофон, параллельно.
3. **P01** (GPT-A) — каркас приложения, версия Flutter, сборка Android в CI. Перед запросом — `rebase` на свежий `main`; всё уже слитое должно остаться зелёным на новой версии Flutter.
4. **P07** (GPT-A) — отрисовка мусхафа; до слияния P03 работает на поддельных данных.
5. **P08** (Астра) — сборка прототипа из всего выше и сборка APK для владельца.

## Что нельзя

Всё из раздела «Non-negotiable rules» в [`AGENTS.md`](../AGENTS.md). Главное: не писать и не менять арабский текст, не коммитить шрифты, модели, записи и секреты.
